# Verified Service Point + Routing Contract — v0.24

## Purpose

NitiKube must not design a kitchen, bathroom or furniture layout as if water, drainage, electrical, gas, exhaust, data or HVAC services exist wherever convenient.

The service-point layer therefore represents **surveyed or otherwise verified service coordinates as evidence**, then evaluates whether explicit design targets can be connected to compatible service points under transparent routing assumptions.

The current model answers a deliberately narrow question:

```text
verified service points
+ explicit planner target coordinates
+ explicit allowed service kinds / distance constraints
→ deterministic assignment
→ PASS / FAIL-style feasibility evidence
```

It does **not** claim to calculate a construction-ready route.

---

## Service point evidence

Schema:

```text
nitikube.service_points
schema_version: 0.24
```

Each service point records:

- globally unique `point_id`
- authoritative `room_id`
- `kind`
- `x_ft`, `y_ft`
- optional `z_ft`
- `verified` state
- evidence/source label
- optional note

Supported kinds currently include:

- cold water
- hot water
- drain
- electrical
- gas
- exhaust
- data
- HVAC condensate
- other

Coordinates use the same floor-plan coordinate system as `nitikube.verified_geometry`.

When verified room geometry is available, a service point outside its declared room is rejected.

### No inferred service points

A room-aware template may list the available verified room IDs, but it intentionally contains an empty service-point list.

NitiKube does **not** create a sink drain because a room is called "Kitchen", or an electrical point because a bed/desk exists. The coordinates must come from survey/evidence.

---

## Service targets

A `ServiceTarget` represents the actual planner object that needs a service connection.

Examples:

- kitchen sink centre
- hob centre
- refrigerator centre
- bathroom WC centre
- basin centre
- shower centre
- bedroom desk centre
- drawing/dining TV-console centre

The module includes deterministic adapters that derive target coordinates from the actual candidate geometry generated by the existing kitchen, bathroom, bedroom and generic room-layout planners.

That means service evaluation can vary **by candidate layout** rather than using one generic room-centre distance.

---

## Routing requirements

Schema:

```text
nitikube.service_routing_brief
schema_version: 0.24
```

Each requirement contains:

- `requirement_id`
- target ID
- one or more allowed service kinds
- optional maximum route distance
- required vs optional state

No service-kind mapping is hidden inside the routing engine. For example, whether a hob requires gas, electrical, or both belongs in the explicit routing brief / product evidence.

---

## Assignment semantics

### Same-room constraint

A service point is currently eligible only when its `room_id` matches the target room.

Cross-room / shaft / riser routing is a later graph-routing layer and is not silently approximated here.

### Verified-only constraint

Unverified service points cannot satisfy routing requirements.

### Allowed-kind constraint

A point must match one of the requirement's explicitly allowed service kinds.

### Optional maximum distance

If `max_route_ft` is provided, points beyond that straight-line distance are excluded.

The limit is a supplied scenario/evidence input; it is not a hidden plumbing/electrical standard.

---

## Distance modes

### `plan`

Uses XY Euclidean distance in the floor-plan plane:

```text
d = sqrt((x2-x1)^2 + (y2-y1)^2)
```

### `3d`

Uses XYZ Euclidean distance:

```text
d = sqrt((x2-x1)^2 + (y2-y1)^2 + (z2-z1)^2)
```

If either endpoint lacks authoritative height in 3D mode, the distance remains unknown. A required service therefore fails rather than silently substituting zero height.

---

## Unique vs shared service points

By default:

```text
allow_shared_points = false
```

Each verified service point can satisfy at most one requirement. The deterministic solver searches for the **minimum-total-distance feasible unique assignment**, rather than greedily taking the nearest point one requirement at a time.

If the design/evidence explicitly permits sharing:

```text
allow_shared_points = true
```

multiple requirements may use the same point.

This is only an assignment semantic. It does not mean the physical service has sufficient capacity for multiple loads.

---

## Required vs optional requirements

If a required service cannot be assigned, routing is infeasible.

Examples include:

- no verified point of an allowed kind
- all matching points exceed an explicit maximum distance
- required 3D height is unknown
- unique point assignment is impossible

If an optional service cannot be assigned, the result remains feasible but records a warning.

## Current planner adapters

The deterministic core can create service targets from:

- `KitchenCandidate`
  - sink
  - hob
  - fridge
- `BathroomCandidate`
  - shower
  - WC
  - basin
- `BedroomCandidate`
  - bed
  - wardrobe
  - optional desk
- generic drawing/dining `LayoutCandidate`
  - every placed furniture item

The adapters use the **actual candidate object centres**. They do not use guessed generic locations.

---

## Routing lower-bound boundary

The current distance is explicitly a **straight-line geometric lower bound**.

It is not:

- routed pipe length
- routed cable length
- duct length
- wall/shaft-aware path
- drainage slope field
- pressure-drop calculation
- pipe sizing
- pump/head calculation
- voltage-drop calculation
- circuit/load sizing
- ventilation static-pressure calculation
- gas-system safety design
- waterproofing design
- code-compliance certification

Walls, vertical risers, shafts, bends, penetrations, routing zones and service-network topology are not yet included.

Therefore a short straight-line link can still be impractical in the real building.

## Fail-closed behavior

NitiKube does not silently accept:

- service points outside verified rooms
- duplicate service point IDs
- unknown service kinds
- requirements without allowed kinds
- requirements referencing unknown targets
- required services with no candidate point
- required 3D links with missing height
- impossible unique assignments

---

## Next layer

The next major integration should make service routing part of candidate feasibility itself:

```text
planner candidate
→ geometry feasibility
→ verified service target extraction
→ service assignment feasibility
→ candidate accepted/rejected
```

After that, routing should advance from straight-line lower bounds to wall/shaft-aware path graphs and discipline-specific engineering calculations while retaining the same evidence provenance.
