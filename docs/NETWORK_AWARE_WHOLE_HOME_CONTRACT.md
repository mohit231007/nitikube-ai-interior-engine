# NitiKube v0.28 — Network-Aware Whole-Home Contract

## Purpose

v0.27 introduced a verified graph for wall/shaft/riser/service-corridor routing. v0.28 moves that graph into the actual room-candidate and whole-home decision pipeline.

The permanent service-aware feasibility rule becomes:

```text
overall candidate feasible
    = geometry feasible
      AND configured verified-network service feasible
```

A geometry score is never allowed to compensate for a missing required route.

## Pipeline

```text
verified geometry
      +
explicit room brief
      +
verified service points
      +
verified service network
      │
      ▼
room candidate generation
      │
      ▼
geometry gate
      │
      ▼
actual candidate service targets
      │
      ▼
bounded target → access-node connector
      │
      ▼
shortest compatible VERIFIED graph path
      │
      ▼
service feasibility gate
      │
      ▼
optimizer promotion contract
      │
      ▼
whole-home constrained optimization
      │
      ▼
provenance-hashed design package
```

## Explicit network policy

Rooms with `service_rules` require a `network_routing.max_target_access_ft` value at project scope or room override scope.

The system does not invent this connector allowance.

Default safety flags:

```json
{
  "require_verified_network": true,
  "same_room_target_access": true
}
```

Room-level `network_routing` values override project-level values deliberately and remain preserved through the hashed brief artifact.

## Candidate target semantics

The route starts at the actual deterministic target coordinate generated by the room planner:

- kitchen: sink / hob / fridge;
- bathroom: shower / WC / basin;
- bedroom: bed / wardrobe / optional desk;
- drawing/dining: furniture item targets.

Required service rule referencing a target absent from a candidate is a failure.
Optional service rule referencing an absent target is a warning.

## Candidate metrics

After network evaluation, routed metrics are added without rewriting geometry score:

- `service_network_total_route_ft`
- `service_network_max_route_ft`
- feature `service_network_evaluated`

Failures/warnings carry `service_network:` provenance.

## Optimization boundary

The existing explicit optimizer promotion contract remains unchanged:

- explicit cost model;
- explicit quality score;
- explicit durability score;
- explicit aesthetics score;
- explicit comfort score;
- explicit maintainability score.

Network feasibility changes whether an option is eligible. It does not silently become a preference score.

If any required room has no feasible optimizer option after network filtering, whole-home optimization does not begin.

## Package provenance

A feasible v0.28 design package includes and hashes:

- verified geometry artifact;
- generated room option artifact;
- verified service-point artifact;
- verified service-network artifact;
- network-aware whole-home brief artifact;
- explicit project network-routing policy;
- professional verification flags.

The package is re-hashed after these fields are added and remains compatible with `verify_design_package_hash`.

## Rooms without service rules

No service rule means:

```text
service_status = not_configured
```

It does **not** mean PASS.

This preserves the evidence contract and permits rooms that genuinely have no configured service requirement to continue through the base geometry/optimizer pipeline.

## Model boundary

v0.28 validates geometric route existence and route length through verified graph evidence. It does not calculate or certify:

- pipe diameter;
- water pressure/flow;
- drainage slope/hydraulics;
- electrical load or circuit sizing;
- conductor sizing;
- voltage drop;
- gas safety;
- duct size/pressure loss;
- fire stopping;
- structural penetrations;
- waterproofing;
- jurisdictional code compliance.

Those must remain explicit downstream discipline layers.
